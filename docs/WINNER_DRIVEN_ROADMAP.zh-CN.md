# MedSeal-MBT：获奖项目对标后的下一轮升级方案

方案版本：1。制定日期：2026-10-12。源码基线：`6800741e184169c3535568a9e758b1dddc98e39e`。

**本文件是待执行方案，不是实现完成记录。** 本轮研究没有修改 MedSeal 功能代码、运行新的功能验收或发布新版本。13 项逐项研究、48 处固定源码证据和证据边界见[完整对标报告](WINNER_RESEARCH.zh-CN.md)。

## 1. 目标与优先场景

继续在原 MedSeal 仓库和提交历史上迭代。目标是：**可解释、可验证、保持研究可用性的 DICOM 数据准备工具库与本地工作台**。

它解决研究机构把影像交给研究团队时的四个实际问题：哪些身份信息如何处理、跨批患者与随访怎样保持一致、像素与空间/强度语义是否仍可用、谁复核过且接收方如何独立验证。签名证明交付内容和授权记录的绑定；影像用途及隐私风险由另外的验收证据证明。

首个深化场景选为**受控目录中的胸部经典 CT 系列，用于研究数据整理、强度统计与体积/空间处理**。优先限定：经典 CT SOP、一个对象一帧、Explicit VR Little Endian、未压缩 16 bit 单色、固定来源域。合成和公开可再分发 phantom 数据先验证算法，再用具备授权与来源说明的代表性数据验证实际用途。来源系统先定义为受控本地导出目录，接收方先定义为独立研究工具链和目录接收器；真实 PACS 连接作为另一个适配与现场验收范围。

已有 SC 工程预览与严格拒绝行为保留。MR、Enhanced CT、多帧、压缩像素、分割/SR/RT 对象等按独立 Profile 扩展，不因为 SOP 名称能被读取就声称完整支持。识别性像素、烧录文字、特殊厂商结构和超出 Profile 的病例仍需明确阻断或责任审核；不自动裁剪像素来掩盖风险。

## 2. 现状：已有基础可以继续利用

[企业实施状态](ENTERPRISE_STATUS.md)与[原验收账本](evidence/enterprise-acceptance.json)记录了严格策略、稳定身份、认证加密、封存与恢复、流式像素、人工放行绑定、签名与独立验签、目录回执、离线安装和合成演练。已有核心是本轮升级的基础，不重做 P0–P7。

仍需完成的软件与实际用途门槛包括逐规则来源、完整限定 IOD 条件、历史引用、重复转换与交付、日期时间语义、全窗口故障和代表性体积；实际来源、独立审查、真实操作/接收用途也尚未验收。旧计划中的“完整 CT/MR”“所有平台”“生产现场”不能因本方案完成了更窄场景而被整体改成完成。

| 证据等级（MedSeal 本方案定义） | 能够证明什么 | 不能据此升级的承诺 |
| --- | --- | --- |
| M0 源码/文档 | 存在接口和设计 | 功能已可运行 |
| M1 合成自动验收 | 固定版本、限定样例、性质和负例通过 | 真实影像、责任人和接收用途通过 |
| M2 独立兼容与用途复现 | 外部校验器/消费者在固定语料上复现 | 机构现场、所有厂商或所有平台通过 |
| M3 受控现场验收 | 指定来源、用途、责任人、运行环境和接收系统签字 | 超出认证范围的普遍生产能力 |

这个分级是吸收 MoUI 的证据分层思路后为 MedSeal 新定义的体系；不沿用其 L1–L3 含义，也不虚构一个成熟度百分比。

## 3. 六项关键升级，八个实施阶段

六项工作是：①标准与规则解释；②独立质量实验室；③跨批身份/时间/交付语义；④研究影像可用性；⑤恢复与安全不变量；⑥公共 API、本地工作台和完整交付体验。把它们拆成 W0–W7，每一阶段有独立产物和验收，避免与已执行的 P0–P7 混淆。

| 顺序 | 阶段 | 前置条件 | 完成后的用户收益 | 工作量与不确定性 |
| --- | --- | --- | --- | --- |
| W0 | 规则账本、结构化解释与公共契约 | 当前基线 | 知道每个字段为什么被这样处理，API 状态明确 | 中；需核对标准条款 |
| W1 | 独立符合性与差分质量实验室 | W0 | 每个支持声明都有可重跑正反例与独立证据 | 大；夹具与参考工具最关键 |
| W2 | 跨批去重、历史引用与时间语义 | W0/W1 | 增量导入真正复用，随访关系与交付记录可靠 | 大；数据迁移和幂等协议复杂 |
| W3 | 经典 CT 系列与研究可用性契约 | W1/W2 | 脱敏结果能进入明确的研究流程 | 大；来源与用途验收决定范围 |
| W4 | 状态模型、故障矩阵与性质/模糊测试 | W0–W3 核心契约稳定 | 能解释和复现恢复、异常、发布与回执行为 | 大；文件系统证据需分平台 |
| W5 | 本地工作台与自包含解释报告 | W0 可做早期只读原型；完整交付依赖 W2–W4 | 管理员可以查看、复核和操作闭环 | 中到大；安全边界与大列表体验 |
| W6 | 仓库外消费者、发行与镜像一致 | W1–W5 | 新开发者能复用，新用户能独立安装 | 中；registry/镜像与安装平台 |
| W7 | 新操作者与实际研究接收验收 | W3–W6 | 有明确用途、责任和运维证据的有限生产版本 | 依赖真实来源与接收方 |

工作量用于比较复杂度，不是承诺日历周期。W1 的小夹具集、W4 的已有故障回归贯穿其他阶段；W5 可以先呈现合成数据的只读解释，但不提前把不成熟的交付功能放开。

## 4. W0：建立规则账本与可解释契约

**借鉴来源：moon_graphql、Frontier Lab、moonsic、MoUI。**

当前 `src/conformance/profile.mbt` 以部分字段数组实施约束，`PathRule` 只有少量匹配字段，变换事件主要是 path/rule/action。它们已经有用，但不能回答某条规则来自哪里、条件为何成立，以及哪个负例证明它不会无声保留身份信息。

新增一份机器可读 Rulebook，建议放 `resources/rules/rulebook-v1.json`。每项包括稳定规则 ID、固定 DICOM 版本/章节/表行、适用 SOP/Profile/Sequence 上下文、Type/VR/VM、条件表达、动作、实现位置、正反例 ID、支持等级和变更说明。字段字典来源与脱敏规则来源分别记载。沿用项目当前固定的 DICOM 2025e，标准升级用显式迁移。

输出版本化 `RuleDecision` 与 `ValidationIssue`：字段路径、规则 ID、标准出处、条件的结构化判定、最终动作、阻断代码、验证阶段和证据 ID。未知条件的求值使用 True/False/Unknown；Unknown 不能被默认成 False 并绕过条件性必需字段。Type 1C/2C 的有条件必需性和描述字段优先级不是同一种概念。

解释分三层：配置解释、对象执行解释、集合关系解释。公开输出只包含审查过的结构与规则信息；原值、患者身份、原始 UID/日期、映射密钥/偏移、输入摘要和本机路径只在私有上下文中使用。错误信息也经过同一输出边界，不能仅移除主报告里的原值。

公共 API 新增门面，建议为 `api/dicom`、`api/policy`、`api/validation`、`api/explain`。旧 `/src/` 导入先保留兼容包装。以私有构造器或受控工厂建立 `ValidatedObject`、`ConvertedObject`、`ReviewEvidence`、`AuthorizedPackage`；类型阻止误用，但反序列化数据必须重新验证摘要、版本和授权，不能当作不可伪造的证明。

**产物：** Rulebook、JSON Schema、结构化解释 API、状态与错误契约、四个合成解释案例及逐规则索引。

**验收目标：**

- 声明支持的规则 100% 有来源、实现、正例和负例；缺项使文档/门禁失败。这个比例按规则覆盖计算，不按代码行覆盖。
- 条件适用、不适用、Unknown、冲突分别有案例；未知身份字段、必要字段删除、规则覆盖越权全部阻断。
- 同输入与配置顺序变化产生同一规范策略摘要；执行决定可复现，不依赖 JSON 字段顺序。
- 用合成身份“金丝雀”值检测公开 JSON、HTML、错误、日志、SVG：原值、原路径、原始摘要与日期偏移出现次数为 0。
- 现有 CLI、旧导入路径和现有审核/签名绑定回归通过，原有行为变更必须进入迁移说明。

## 5. W1：让支持声明成为独立可重跑的证据

**借鉴来源：tokenizers-moonbit、moon_graphql、MoonFrame、markitdown。**

建设 DICOM 质量实验室，建议用 `conformance/manifest.json` 记录每个夹具的 ID、来源/许可、文件哈希、输入类型、测试目的、预期拒绝/通过、适用规则、参考工具版本和依赖哈希。可提交的夹具以小型合成与许可明确的非患者数据为主；真实数据仅保存私有运行，公共记录不含原文件、原值或可链接摘要。

独立验证分四条链，避免错误的“一次通过等于全部安全”：

| 验证链 | 使用什么依据 | 通过说明 |
| --- | --- | --- |
| 编解码差分 | 固定版本 pydicom 与独立生成的预期模型；语义规范化后对比 | 读取/写入字段值和结构一致 |
| IOD 与值符合性 | 固定标准条款、自有条件测试、dciodvfy 原始诊断 | 所声明的模块/条件得到检查；校验器自身范围也记录 |
| 去标识策略 | 从标准与项目保留用途推导的原创建模预期 | 动作符合所选策略；不照抄其他工具的默认脱敏结果 |
| 研究可用性 | 独立像素/几何/时间/引用工具和契约 | 接收用途要求的语义保持 |

测试按 valid、malformed、unsupported、resource-limit、privacy-risk、conditional 六类组织。至少覆盖长度截断、非法 VR/VM、重复标签、未定义长度/嵌套边界、字符集、UID、必需字段、关联所有权及像素跨度。独立参考遇到宽松接受不代表 MedSeal 必须接受；差异进入已解释差异清单。

必需夹具缺失直接失败。optional 来源可单列 skipped，但必须显示实际 executed/passed/failed/skipped，不能把“全部 0 次执行”报告为全部通过。发布档的声明范围中不允许未解释 skipped。

**产物：** 固定夹具清单、分类测试运行器、规范覆盖矩阵、独立原始诊断、差分报告，以及与源码/程序/依赖绑定的运行证据。

**验收目标：**

- 初始核心发布档不少于 120 个有独立预期的分类案例，之后随规则增加；这只是规划目标，不是当前测试数量。每条声明规则仍必须各有正负证据，120 个不能代替覆盖要求。
- 公开库 Native/JS/wasm/wasm-gc 的目标无未解释语义差异；系统提供方按实际支持平台另验收。
- 每个独立 Error 已修复或导致对象拒绝；Warning 逐类说明对目标用途的影响，不通过过滤 Warning 制造干净报告。
- SC 的已有验收继续保留；CT 未取得完整所选 Profile 的规则与独立证据前，保持实验状态。
- 不采用获奖项目的测试数量或性能数据作为 MedSeal 的达标线；语料、用途和风险不同。

## 6. W2：让增量处理真正保持关系并避免重复交付

**借鉴来源：MoonFrame 的明确数据语义、moonsic 的状态类型、raft 的持久化协议。**

现有身份库已能跨批复用患者/UID 和拒绝原内容/归属冲突，但只“再次映射得到同一个 UID”还不等于不重复转换，更不等于历史引用可安全解析。

新增私有对象/转换/发布/目的地账本。去重键至少绑定项目、来源域、原始内容的私有认证索引、策略/字典/规则版本、算法/运行程序指纹与输出摘要。内容相同但策略或转换程序变了，不能误用旧结果。私有索引、源 SOP 与缓存路径不出现在公开报告。缓存命中仍检查载荷存在、摘要与对应审核是否有效。

状态区分 Seen、Converted、Reviewed、Published、Acknowledged。引用在本批找不到时，必须查询同项目/来源域及目标交付域中的已发布记录，验证患者/归属、SOP Class 和目标输出；只预留映射或只转换未交付的目标不能作为已交付历史引用。默认阻断未解决引用，并输出可操作的“补齐目标批次”说明；不要依赖 `allow_external=true` 的笼统放行。

目录交付使用 outbox、不可变包 ID、目的地身份及逐对象核验回执。可重试动作按幂等键执行，回执丢失后核验实际目标再重建。旧对象/回执被删除或篡改必须检测；禁止单凭数据库的 acknowledged 字段跳过文件核验。不承诺任何任意远程系统的 exactly-once，未来 PACS 适配需独立协议验收。

完善日期时间模型：DA、DT、TM 分开解析，记录精度、小数秒、显式时区与缺失值语义。完整 DT 用同患者一致偏移保留允许的相对间隔；不把无时区值偷偷转成 UTC，不为低精度 DT 补出不存在的日/秒。只有年月等不足以进行无歧义按日平移的 DT，按 Profile 明确清空/移除/阻断；单独 TM 没有日期上下文时不擅自按整天偏移。DA 仍遵循固定标准的完整日期格式，不引入错误的部分 DA 支持。

**产物：** 数据库 schema 迁移/备份与回退工具、私有缓存账本、历史引用解析器、outbox/回执协议、时间精度模型与迁移文档。

**验收目标：**

- 五批固定患者随访中假名、UID 与已定义偏移一致；不同项目/来源域保持隔离，原内容/归属冲突 100% 拒绝。
- 同语义运行键的完整重复输入不再次转换、不产生重复最终对象；缺失/篡改缓存重新验证或明确失败。
- 策略/程序/目的地/授权变化各有案例；不复用失效审核和旧目的地回执。
- 历史引用通过、目标尚未发布、跨患者、跨项目、跨来源、错误 SOP Class、目标丢失/篡改均有明确预期。
- 闰年、世纪边界、跨午夜、小数秒、时区、低精度、非法值、年份溢出及合法闰秒边界按标准建模并测试；只在定义了相同时间语义的域内检查间隔保持。
- 每次交付满足计数守恒：发现对象 = 新转换 + 可信复用 + 拒绝；授权对象 = 新交付 + 核验过的已交付。中途失败不会报告整体完成。

## 7. W3：证明经典 CT 结果仍能用于明确研究用途

**借鉴来源：markitdown 的语义质量实验室、linear-algebra 的不变量、moon_graphql 的分范围符合性。**

支持目标是一个明确的 CT 系列 Profile，不是所有 CT/MR。先实现经典 CT 所需模块和条件规则：按固定标准列出 Patient/Study/Series/Frame of Reference/Equipment/Image/CT Image 等适用模块，逐项判断 Type 1/2/1C/2C；只有矩阵无遗漏且规则通过，才能称该限定 Profile 完整。厂商扩展超出已审查字典时继续拒绝，不能为提高接收率静默保留。

研究可用性单独列四个契约：

1. **像素。** 载荷字节/独立解码体素保持一致；Pixel Representation、Bits Stored/High Bit 等语义正确。烧录风险未解决时不获得交付许可。
2. **强度。** Rescale Slope/Intercept 与单位保持所声明研究语义；在已确认 HU 适用的 CT 域检查重建数值，不能对不具备相应单位依据的对象强称 HU。
3. **空间。** Pixel Spacing、Image Orientation/Position、Frame of Reference 及切片排序形成一致三维坐标；检查缺片、重复位置、方向混合和间距异常。是否阻断由明确系列契约决定，不使用泛化阈值删除有效病例。
4. **纵向关系。** 同患者随访保持身份、集合引用及允许保留的时间间隔；源日期和偏移只用于私有验收。

引入固定版本独立研究读取工具（优先 pydicom + SimpleITK 或经评估的等价工具），用独立的预期几何与可用数据转换作对照。许可/来源合适的公开 phantom 可形成可分享回归；实际来源可形成私有测试记录。成功生成 NIfTI/数组只证明特定读取路径，不自动证明临床可用或医疗器械认证。

**产物：** `ct-classic-research-v1` 契约、完整范围矩阵、独立体素/强度/几何报告、系列关系清单和接收示例。

**验收目标：**

- 转换前后体素差异数为 0；在 HU 契约适用处，独立计算的强度差异为 0，无法成立时解释并阻断该用途声明。
- 所保留几何字段语义一致；独立坐标比较初始目标为方向分量误差 ≤1e-6、物理坐标误差 ≤1e-4 mm。容差依据、量纲和数值转写影响进入契约；不得为让测试通过不断放宽。
- 至少三组来源/形成方式不同的授权或可再分发系列，每组 50+ 切片，并有结构/方向/间距异常负例；合成病例算算法证据，不冒称三台真实设备。
- 独立接收脚本完成切片排序、数组读取和所声明的强度/空间计算，结果符合预期；M3 还要求代表性真实来源与接收方确认。
- Profile 外格式、识别性像素、不能解释的厂商字段、未知条件和空间异常有明确状态与阻断路径。

## 8. W4：恢复、发布和交付都有确定性模型

**借鉴来源：raft-moonbit、MoonFrame、linear-algebra。**

保留已有真实 SIGKILL/空间不足/竞争验证，增加 MoonBit 作业状态机与简单独立参考模型。SQLite 日志、文件转换、审核、发布和交付使用同一合法转移规范；适配器只承担系统动作，不自己另造允许转移。模型里的崩溃、遗漏、重试事件必须能导出为真实复现脚本的事件描述。

每个持久化窗口登记稳定故障点：写入前后、文件同步前后、目录同步、rename 前后、数据库提交前后、审核固定前后、签名封装前后、目标复制前后、回执固定前后。区分 process-crash、OS/power-loss 和持久存储错误，后两类没有实证时保持未认证。

系统不变量至少包括：未审核不可发布；源/策略/程序改变旧审核失效；同 SOP 不允许矛盾内容；可见完整包均可独立验签；partial 不冒充 complete；输入封存不变；私有材料不能进入公开报告；旧有效提交不被失败重试覆盖；取消不清理他人资产；交付计数与核验对象一致。

模糊测试优先 parser、长度/深度/字符集、策略 JSON、规则条件、公开清单和接收器。资源预算超出返回结构化拒绝，不允许无界分配/递归。性质测试比较流式/内存路径、同域稳定映射和关系守恒，并验证生成器实际覆盖目标分支，避免空洞通过。

**产物：** 状态转移表、故障点目录、可重放模型运行器、不变量报告、收缩反例、fuzz corpus、固定负载资源报告。

**验收目标：**

- 所登记提交窗口全部有至少一个强制中断与恢复案例；每次恢复均验证不变量，不能只检查目录存在。
- 每次 PR 跑固定回归和至少 100 个 seed × 200 个有效状态事件；扩展档至少 1,000 seed × 500 事件。执行/转移覆盖有计数；发现反例保存 seed、事件序列与最小化结果。
- 初始 fuzz 完成至少 100,000 次有效输入/变异且无未解释 crash/超时/预算突破；记录语料、执行数、时间预算和工具版本。数量是本方案门槛，不是数学正确性证明。
- 1/16/64/120 MiB 和 1,000/10,000 对象既有基准在新版本重跑；另跑 1/8/32 GiB 系列负载，每档五次，分别记录墙钟、CPU、Native 子进程 RSS、协调器/总进程资源、临时空间和恢复成本。
- 同环境与语义基线比较：120 MiB 单对象 Native RSS 初始回归上限 64 MiB；10,000 对象整个作业初始目标 256 MiB，需要先明确包含哪些进程；32 GiB 像素总量不得造成同比例 RSS 增长。元数据/对象数增长另有预算，不误称绝对恒定空间。
- 本机模拟和强杀结果保持 M1；未做真实断电和平台持久性测试，不自动把相关条目升级到 M3。

## 9. W5：本地工作台把核心能力交给实际操作者

**借鉴来源：Frontier Lab、aitne、Hex Editor、MoonCharts、MoonMarkMind。**

交互围绕五个页面组织：

| 页面 | 用户做什么 | 复用哪个核心 |
| --- | --- | --- |
| 作业与导入 | 选受控目录、查看发现/复用/拒绝、恢复/取消 | 现有封存、W2 账本、W4 状态机 |
| DICOM 检查 | 按字段/Sequence 路径定位 VR/VM/条件错误，私有只读像素预览 | MoonBit parser、W0/W3 规则与受限流式读取 |
| 规则解释 | 查看动作依据、条件、首次阻断及规则变更差异 | W0 RuleDecision 与 W1 证据索引 |
| 风险复核 | 按对象复核像素/来源风险并绑定审核证据 | 现有审核门禁；不在前端另外判定“安全” |
| 交付与报告 | 签名发布、独立验签、目录回执、导出受限解释报告 | 现有签名/接收器与 W2 outbox |

浏览器视图优先用 MoonBit 的 JS/wasm 核心；DOM/进程/文件由轻量宿主适配。先做小型视图与虚拟列表，不先引入全套 MoUI 原生渲染系统。aitne、MoonCharts 等依赖需做当前工具链、许可证、体积与 API 兼容评估后固定版本，使用它们只是可选实现选择。

真实工作台在本机受控环境运行，采用 loopback 服务或等价本地 IPC，限制文件选择根目录，服务端重查每次操作的权限、摘要和合法状态。若采用 HTTP，必须检查 Host/Origin、拒绝跨站请求、使用会话能力与 CSRF 防护并测试 DNS rebinding；会话密钥不放 URL 或输出日志。进程调用使用受控参数列表，不能拼接用户字段为 shell 命令。

分离两个应用能力集：公开合成演示只展示可解释核心与模拟状态；真实审核工作台必须绑定本地授权配置和当前输出。公开页面永远没有生产发布权限。只读像素预览不用于诊断，也不把“看起来没有文字”自动变成通过。

离线 HTML/SVG 报告用显式字段允许列表生成；无 CDN、远程字体/图片、遥测或患者原值。私有对比视图需要明显私有标记，不能被公开导出按钮带走。实际交付包中允许的假名/映射 UID 也不自动进入公开展示报告。匿名汇总小群体计数按接收用途做抑制，公共比赛演示统一用合成数据。

**产物：** 本地工作台、独立合成在线/离线 demo、受限 HTML/SVG 解释报告、用户手册与 UI 自动验收。

**验收目标：**

- 首次使用者按手册完成导入→解释→处理阻断→复核→签名→独立接收，成功状态与证据均能定位。
- 10,000 对象使用虚拟/分页列表；只处理当前可见像素，切换病例不会全量载入。首屏与筛选在固定参考环境上的目标 ≤2 秒，环境和数据大小记录。
- 修改策略/输出/授权/程序后，界面和服务端均拒绝旧放行记录；离线/中断/取消没有假成功提示。
- HTML/SVG 输入含 script/onerror/javascript/远程资源时不执行、不请求外网；公开产物的身份金丝雀检测为 0。
- CLI 与工作台相同请求得到同一策略摘要、规则决定和输出验证结果；UI 不拥有另一套转换引擎。

## 10. W6：把库、安装包和公开版本交付一致

**借鉴来源：MoUI 的外部消费者、GraphQL 的薄工具、MoonMarkMind 的库/应用双交付。**

新增 `examples/consumer` 的仓库外验收：一个只依赖公共 DICOM/规则 API 的转换例子，一个复用解释/验证报告的读取例子。测试复制到独立目录，验证依赖实际来自发布归档/registry，并在移走原 checkout 后构建与运行；没有源码树可见时仍可成功。

源模块、版本常量、README、CHANGELOG、tag、GitHub release、GitLink 镜像、Mooncakes 和安装包清单使用同一个版本来源。项目现有文档记录源码候选 0.2.0 与公共包 0.1.1 尚未同步；执行发布前重新读取实际 registry/镜像，避免根据旧状态误报已发布。

版本建议：先形成带新增规则/API/场景的 0.3.0 候选；所选 Profile 未验收的能力标 experimental。1.0 只对应通过 W7 的有限场景，保留其他 Profile/platform 的 partial/unsupported，不承诺“全医疗数据生产工具”。旧接口按语义版本与迁移说明维护。

离线包沿用当前固定哈希依赖、清单检查、SBOM/许可证及隔离安装机制。每个支持平台必须真实打包、断网新安装、安装后闭环；不要从核心在 Windows 编译通过推出 Windows 私有企业适配支持。

**产物：** 独立消费者、稳定 API 文档与可运行教程、版本迁移、候选发行包、公开支持矩阵和镜像/包一致性证据。

**验收目标：**

- 归档消费者与 registry 消费者各独立构建、执行关键流程；引用原 checkout 即失败。
- 四后端核心和实际承诺的平台适配均跑相应门禁；README 明确核心能力与系统提供方差异。
- checksum 不符、额外文件、被改依赖/载荷在安装前拒绝；全新断网安装后解释、转换、恢复、审核、签名与接收演练通过。
- 包名、版本、tag、镜像 commit、Mooncakes 内容与制品指纹可核对；发布完成以读回平台结果为准。
- 完整保留原项目贡献历史，研究来源与实际采用的依赖分别标注，不为代码行数凑功能。

## 11. W7：以新操作者和实际接收用途收尾

**借鉴来源：获奖项目的可复现验收路径，并补上医学数据场景必须有的用途证据。**

先完成本地合成/phantom 操作演练，再验证授权的代表性来源。固定研究任务、输入 Profile、接收工具、操作系统/文件系统、密钥/备份流程、审核责任与异常处置；只读研究和对外交付权限分开配置。选择数据授权、来源说明、独立审查和现场责任人时需要实际主体材料，代码不能代填。

新增演练脚本和操作者验收单：首次全量、两次增量、纯重复批、历史引用批、冲突批、策略变更、强杀恢复、空间不足、取消、包装密钥轮换/备份恢复、丢失/篡改回执、独立接收失败与重试。每个失败说明原因、已交付范围和下一步，运维手册包含恢复证据与退出机制。

独立评审至少覆盖脱敏策略与病例用途，以及私有映射/密钥/审核/交付信任边界；研究读取成功和隐私审核成功分别出具结论。实际审核者不能用 OCR 阴性、签名有效或 AI 判断替代其证据覆盖责任。

**产物：** 实际场景验收记录、操作者反馈及修复、独立审查问题闭环、恢复/备份/事故手册、有限场景支持声明。

**验收目标：**

- 至少一名未参与实现的新操作者独立完成合成全流程，无需修改源码或询问隐藏参数；真实研究接收方按定义用途读入并确认结果。
- 至少一次代表性真实来源的私有验收，保留授权与来源证明；公开 phantom 或合成成功不能代替这一项。
- 严重安全/语义问题为 0 个未解决；可接受残余问题有责任人、适用范围和处置记录。
- 备份恢复后稳定身份与历史交付关系保持；丢失回执和部分失败能可靠核验与重试。
- 运维指标覆盖吞吐、拒绝/待审核/成功计数、恢复耗时、缓存命中、空间和异常率；指标不包含患者身份、原值或可关联的原始摘要。
- M3 按来源/用途/平台逐项达成；没有真实材料的项继续标 requires_field，不能为凑完成率标成通过。

## 14. 参赛展示怎样呈现新增价值

展示主线使用可公开的合成 CT 系列：导入并显示封存 → 点开两条规则看到依据/条件/动作 → 注入未知字段或错误引用并定位首个阻断 → 修正输入并生成新的作业 → 看研究可用性对照 → 处理像素复核 → 签名 → 独立接收 → 再导入随访和重复批看到稳定关系/可信复用。

同时提供三个可被独立使用的产物：Mooncakes 工具库、本地工作台、固定语料与质量报告。展示每个产物的可运行入口、失败案例和已认证范围。核心算法与规则仍在 MoonBit，宿主适配职责明确；标准/字典数据、第三方依赖、原创逻辑和获奖项目研究参考分别说明。

这一组合能突出 MedSeal 在本次 13 项名单中的领域差异及实质新增贡献。它提高可复用、可验收和可展示程度，不构成获奖保证或全生态唯一性证明。

## 15. 现在可以开始的第一步

从 W0-a 落实 Rulebook：先把现有严格属性和 SC 规则逐项写入来源/条件/实现/正反例账本，暴露缺口，再新增结构化解释。随后接 W1 的必需夹具与独立验证；用这些基础支撑 W2 和 W3。工作台可以先展示这四个合成解释案例，完整审核/交付页面在相应核心门槛通过后启用。

到下一轮评估时，不再问“功能有多少”，而是核对：所声明规则是否可追踪、增量是否守恒、影像用途是否可复现、异常是否可恢复、新用户是否能独立使用、接收者是否能独立验收。
