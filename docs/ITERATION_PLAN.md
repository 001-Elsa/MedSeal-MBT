## 结论与项目定位

建议继续迭代 MedSeal-MBT，不需要重新立项。现有工程已经具备一个可继续演进的 DICOM 文件处理核心；下一阶段应从“单文件、固定字段替换”升级为**保留患者分组、检查时间关系和影像引用关系的多文件 DICOM 元数据脱敏库**。

推荐参赛名称：**MedSeal-MBT：面向关联医学影像数据集的一致性脱敏与验证工具**。

核心价值：把一组有关联的 DICOM 文件交给工具，在替换身份信息之后，仍能区分不同患者、保持同一患者的文件关联、保留所选检查日期的时间间隔、维持影像之间的引用，并生成可复核的验证报告。输出可用于合成数据整理、教学和研发联调；像素内容仍需另外检查。

“成熟”的定义是支持范围内行为稳定、失败行为清楚、结果可被独立工具验证，而不是声称覆盖全部 DICOM 或保证完全匿名化。参赛验收和获奖由评审决定，本方案提供可落实的功能与证据路径。

## 四、推荐实现的一条主线

### 1. 策略引擎：规则可解释、默认行为可预测

在当前 Keep / Empty / Replace / Remove 之上增加 UID 映射、患者假名、指定日期偏移动作，支持版本化 JSON 策略、标签与 Sequence 路径匹配、规则优先级、预检和 dry-run。

策略加载时拒绝冲突动作、错误 VR、不合法替换值。规则记录来源、适用标签、条件和测试编号；对未知私有元素默认移除，对未知公共字段按明确规则保留、拒绝或要求复核，不能悄悄宣称它们安全。

保留当前 basic 模式兼容调用，增加推荐的 research 模式：移除私有元素、移除或置空高风险描述性自由文本、开启身份 UID 重映射，并输出剩余风险。字段删除/置空须考虑支持 SOP Class 中的 Type 1/2 要求，不能仅按敏感性随意移除。

### 2. 共享脱敏上下文：多文件保持同一映射

新增 `DeIdContext`，整个作业共用。患者标识优先按数据来源命名空间、Patient ID、Issuer of Patient ID 组合，不能仅靠姓名或 Patient ID；缺失/冲突必须拒绝、隔离或由明确配置决定，不自动合并。

同一患者在作业内使用同一假名，不同患者不得都变成 MEDSEAL-ID。同一原始身份 UID，无论出现在主元素、引用 Sequence 还是 File Meta，都映射为同一新 UID。

第一版优先采用**作业内共享映射**，保证重复扫描和文件排序变化不改变关系；跨作业稳定映射作为可选扩展，需要明确项目隔离和密钥管理。若采用 HMAC，必须先核查可复用 MoonBit 实现、许可证和标准测试向量，不能用普通哈希或自制加密替代。映射状态包含原始身份值，禁止输出到公开审计报告或提交仓库。

### 3. UID 重映射与引用验证：主要技术亮点

- 按角色区分实例身份 UID 与标准 UID；Study、Series、SOP Instance、Frame of Reference 等按支持规则映射。
- 保留 SOP Class UID、Transfer Syntax UID 等标准语义；不能对所有 UI VR 一刀切替换。
- 同步 Media Storage SOP Instance UID 与数据集 SOP Instance UID；File Meta 的实现信息改为工具信息。
- 遍历嵌套引用 Sequence，将引用同步到同一映射表。
- 写后构建对象索引，检查引用是否仍指向正确对象、重复 SOP UID 是否冲突、患者/Study/Series 归属是否矛盾。
- 默认验收闭合集合，未解析引用阻止该集合发布；允许外部引用的模式需显式声明并在报告中标记未验证部分。
- 新 UID 遵循 DICOM 数字组件和最大长度要求，可使用合法 `2.25.<UUID十进制>` 形式，必须检测碰撞。

### 4. 日期偏移：保留检查之间的时间间隔

同一患者、同一作业内所有被策略选中的检查日期使用同一个偏移量。例如两次检查间隔 14 天，转换后仍间隔 14 天。出生日期按策略删除或置空，不因日期偏移功能默认保留。

第一版明确支持完整 DA 的日历运算，覆盖闰年、月末、跨年、非法日期和越界；DT 的时区/精度及 TM 的组合语义待另设支持清单。不能任意给不完整日期补值，也不能把独立 TM 当作日期整体偏移。

日期偏移与假名化仍可能允许关联，不把这项功能表述为完全匿名化。重复处理策略须明确：默认拒绝再次偏移已有处理标记的文件；只有能核对匹配作业状态时才支持安全恢复，不能仅凭标记判定全部规则已完成。

### 5. 多文件作业：两遍处理、受控发布

第一遍检查支持范围、患者分组、UID 与引用关系并准备映射；第二遍逐文件转换和验证，避免把全部 Pixel Data 同时读入内存。

作业目录中包含匿名编号 DICOM、公开审计报告和最终清单。默认遇到硬错误阻止该作业发布；若支持部分成功，必须把它作为显式模式，列出失败对象及影响，不能伪装成完整成功。

暂存区与发布区位于同一文件系统，以目录发布或“最终清单为完成标志”定义提交协议；说明不同系统的原子性边界。断点恢复验证输入是否变化、策略版本是否一致、已完成输出是否正确。

拟新增接口（尚未实现）：

```text
medseal plan <input-dir> --policy research.json
medseal batch <input-dir> --output <new-job-dir> --policy research.json
medseal verify <job-dir>
```

原 inspect / validate / anonymize 保留。库 API 应能直接调用策略、上下文、转换和验证，CLI 仅负责文件编排。

### 6. 输出验证：处理成功与风险结论分开

报告区分转换是否完成、结构是否有效、引用是否通过、所选脱敏规则是否通过、剩余风险是否需要复核。增加元素完整路径、策略版本、规则编号、匿名对象编号和稳定错误码。

对支持规则检查身份字段、私有元素、旧身份 UID、File Meta 与前导区；对 Pixel Data 做字节比较或摘要验证。自由文本检查只能反映配置规则或已知合成标记覆盖，不能证明未知隐私不存在。

像素未检查必须是明确风险项，而非“全部安全”的报告脚注；不得仅凭 Burned In Annotation 标记宣称像素安全。Patient Identity Removed 等标准标记须根据实际实现覆盖审慎设置，不提前写入完整标准 Profile 的合规声明。

## 五、架构与范围

推荐新增四个包：`policy`、`identity`、`batch`、`verification`。日期运算先放 identity 或 deid 内部，复杂度增长后再拆 date，不为目录数量而拆包。

```text
输入集合 -> 预检与对象索引 -> 策略 + 共享上下文
         -> 逐文件转换 -> DICOM 写回 -> 独立验证
         -> 暂存结果与审计 -> 发布作业清单
```

首个成熟版本继续限定 Explicit VR Little Endian 与列出的 SOP Class/规则范围。支持更多传输语法、压缩数据透传、OCR、PACS、DICOMweb、Web 管理后台留待主线完成后的独立版本。

预计新增约 2,300–4,000 行有实质逻辑的 MoonBit 实现，现有实现合计约 4,600–6,300 行；这是粗略规划，不含测试数量目标，也不承诺赛方计数。预算应花在规则、关系和失败行为上，不为参考代码规模添加无用功能。

## 七、成熟项目的验收证据

### 必须通过的场景

1. 两个患者、各两个 Study、每个 Study 多个 Series 和实例：转换前后分组一致且患者假名不同。
2. 一个文件引用另一个文件：主 UID、引用 UID、File Meta UID 同步；打乱输入顺序后仍正确。
3. 深层 Sequence 内身份字段被处理，审计可定位到具体 item，公开报告不含旧值或原始文件名。
4. 标准 Class/Transfer Syntax UID 保持正确；多值 UID 逐值按角色处理。
5. 两次检查的天数差不变；覆盖闰日、跨年、非法与越界日期。
6. 前导区、文件元信息、文件名、嵌套字段分别植入合成标记，转换后在所承诺清理位置均不残留。
7. 保留的文本字节与 Pixel Data 不发生非预期变化；不支持字符集明确报错。
8. 外部引用、重复 SOP UID、缺失患者键、未知 SOP、超限文件均按声明的模式处理。
9. 报告写盘失败、输出写盘失败、恢复时输入变化、并发运行不出现错误成功标志或覆盖输入。
10. 重复输入/重复转换行为可预测，不二次偏移或把已映射 UID 无意再次映射。

### 测试方法

- 保留原回归测试，增加策略、身份、日期、引用、发布协议测试，不以测试条数代替覆盖质量。

- 按 DICOM 标准检查语义；pydicom 能读取不等于完整标准合规。
- 对 parser 做长度/截断/深度等受控变异测试，对转换做顺序不变性、像素保真等性质测试。
- CI 延续检查、构建、测试、接口一致性和打包；在至少一个平台执行跨工具对照。
- 基准先覆盖合成的 100/1,000 文件集合与不同像素体积，记录环境、文件总量、耗时和峰值内存；由实测形成性能承诺，不预先宣称优于其他库。
